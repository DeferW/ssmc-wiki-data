# SSMC Wiki

SSMC Wiki — неофициальная модульная база данных и набор веб-инструментов для
**Space Stories Marine Corps**. Проект состоит из двух репозиториев:
[`ssmc-wiki-data`](https://github.com/DeferW/ssmc-wiki-data) собирает данные из
исходников игры, а [`ssmc-wiki-app`](https://github.com/DeferW/ssmc-wiki-app)
публикует сайт и работает с готовыми контрактами.

- [Планы и TODO](https://github.com/DeferW/ssmc-wiki-app/blob/main/docs/ROADMAP.md)
- [Руководство контрибьютора](https://github.com/DeferW/ssmc-wiki-app/blob/main/docs/CONTRIBUTOR_GUIDE.md)

## Роль репозитория

`ssmc-wiki-data` — набор воспроизводимых сборщиков. Он читает прототипы,
локализацию, ресурсы и явно заданную конфигурацию, разрешает игровые связи и
публикует устойчивые JSON-контракты с готовыми ассетами. Сгенерированные файлы
находятся в `data/` и не редактируются вручную.

## Общая архитектура

```text
исходники игры + config сборщика
            ↓
ssmc-wiki-data/scripts/<module>
read → resolve → normalize → validate → publish
            ↓
ssmc-wiki-data/data/<module-id>
публичный JSON-контракт + ассеты
            ↓ точная замена при deploy
ssmc-wiki-app/public/data → dist/data
            ↓
loader + types → логика модуля → UI
            ↓
GitHub Pages → пользователь
```

`data/<module-id>/` — граница между репозиториями. При deploy приложения свежий
`data/` полностью заменяет `public/data/`, поэтому удалённые сборщиком файлы не
остаются в публикации. Браузер получает сайт, JSON и ассеты с одного GitHub
Pages-адреса и не обращается к GitHub Raw при открытии модулей.

## Архитектура сборщика

```text
config/                    редактируемые настройки и выбор источников
scripts/common/            общие форматы и разделяемая предметная логика
scripts/<module_package>/  изолированный сборщик предметной области
data/<module-id>/          опубликованный JSON-контракт и ассеты
.github/workflows/         проверки и воспроизводимые сборки модулей
requirements.txt           runtime-зависимости Python
pyproject.toml             настройки тестов и статического анализа
```

Каждый сборщик владеет чтением источников, разрешением наследования и ссылок,
нормализацией предметной модели, сериализацией, валидатором, тестами и своей
выходной папкой. Общий код выносится в `scripts/common/` только когда у него есть
несколько реальных потребителей.

Зависимости направлены только вниз: CLI сборщика использует свой предметный
модуль, предметный модуль — общие пакеты, а общий пакет не импортирует конкретный
сборщик. Если один модуль предоставляет другому готовый результат, это делается
через небольшой публичный API, а не через набор внутренних файлов. Так каталог и
карты используют одну категоризацию и одну сборку карточек предметов, не
дублируя правила. Конфигурация невзятых в руки объектов остаётся отдельной от
каталога: такие сущности могут попадать в карту, но не становятся предметами.

## Контракт и изменения

Публичной точкой входа обычно служит `data/<module-id>/catalog.json` с явной
`schemaVersion`. Приложение использует только публичные документы и ассеты;
диагностические индексы и промежуточные результаты могут меняться без обратной
совместимости.

Ломающее изменение типа, структуры или смысла поля получает новую
`schemaVersion`. Сначала здесь публикуется совместимый набор данных, затем
обновляется приложение. Сборка должна быть детерминированной: одинаковые
исходники, конфигурация и commit игры дают одинаковый результат.

## Локальная проверка

Требуются Python 3.11 или новее и зависимости проекта.

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m pip install pytest ruff
```

Перед pull request:

```powershell
python -m ruff check scripts
python -m pytest scripts
```

Параметры конкретного сборщика смотрите через его `--help` или workflow в
`.github/workflows/`. Сборщик должен записывать результат только в принадлежащую
ему папку `data/<module-id>/` и удалять из неё устаревшие файлы.

## Локальная совместимость

JSON публикуется с UTF-8 и LF, одинаково на Windows и Linux. Сериализаторы явно
задают перевод строки, а `.gitattributes` сохраняет LF при новых checkout.
В старых Windows checkout валидатор карт сравнивает `assetBytes` с размером JSON
после нормализации CRLF в LF; реальные изменения содержимого продолжают вызывать
ошибку. Ограничение общего размера проверяется по фактическим файлам.

Для запуска сайта держите `ssmc-wiki-app` рядом с этим репозиторием:
его `npm run dev` и `npm run build` сами подготавливают снимок из `data/`.
После пересборки данных обновите снимок командой `npm run data:sync` в app.
Применение категорий и версия браузерного кэша принадлежат app-снимку.

Исправленная классификация инструментов применяется при следующей сборке
каталога и предметов карт. Generated JSON не переименовывается и не исправляется
вручную; для его обновления нужны соответствующие сборщики и игровые исходники.


## Контракт данных с ssmc-wiki-app

`data/` — только результаты workflow. Исправления делаются в сборщиках и тестах;
нельзя дописывать поля в готовые JSON вручную или отдельным скриптом миграции.

| Workflow | Результат | Потребитель в app |
| --- | --- | --- |
| Build catalog | catalog/index.json, catalog/catalog.json, спрайты | Каталог, сборка оружия, обвесы, боеприпасы, броня, калькулятор, сравнение, отдача |
| Build map data | maps/catalog.json, static-items.json, оверлеи, тайлы и спрайты | Карты, инсерты, предметы и объекты карт; оружие карт во всех вкладках калькулятора |
| Build mobs data | mobs/catalog.json, спрайты | Цели калькулятора: здоровье, зрелость, броня направлений, размер и штамм |
| Build chemistry catalog | chemistry/guides.json, index.json, catalog.json | Реагенты, эффекты, рецепты, условия и планировщик химии |
| PR checks | Ничего не генерирует | Линтер, тесты и проверка уже опубликованных данных |

Для согласованного обновления укажите один и тот же SHA игры в `game_ref` всех
четырёх сборок. Значение `master` удобно для отдельного запуска, но ветка может
сдвинуться между запусками. После публикации результатов обновите приложение.

Оба сборщика предметов используют `build_catalog_documents` и
`populate_weapon_statistics`. Новый обнаруженный прототип получает параметры
автоматически; `weaponStats.ballistics`, scatter и recoil содержат оба хвата.
Перед публикацией обоих каталогов `validate_weapon_contract` проверяет эти поля.
Особые неподдерживаемые механики явно помечаются, а не подменяются числами.
Значения C# по умолчанию и алгоритмы проверены по указанному в ballistics commit;
изменение самой игровой механики требует обновления нормализатора и тестов.
